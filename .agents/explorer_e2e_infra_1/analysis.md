# E2E Test Runner and Harness Design Analysis

## Executive Summary
This report analyzes the Next.js frontend codebase, details the behavior and SQLite schema interactions of the 8 core features, and proposes the architecture for an opaque-box, custom E2E test runner and harness. It outlines a complete 4-Tier mapping of 93 distinct test cases to verify the platform under normal, boundary, and adversarial conditions.

---

## 1. Feature Behavior & Code Analysis

### Feature 1: Credentials Login & Signup (Employees and Analysts)
*   **Behavior**:
    *   **Signup**: Employees signup via `/signup/employee` and analysts via `/signup/analyst`. Signup endpoints create unverified/unapproved accounts in the SQLite database, generate a 6-digit verification OTP, and return `success: true`.
    *   **Login**: Login happens at `/login`. Employee login requires `email`, `password`, and `role = "employee"`, checking if `isVerified` is true. Analyst login requires `email`, `password`, and `role = "analyst"`, checking if `isApproved` is true. Valid logins issue a JWT session cookie.
*   **Database Tables**:
    *   `Employee`: fields `id`, `name`, `email`, `passwordHash`, `department`, `isVerified`, `riskScore`.
    *   `Analyst`: fields `id`, `name`, `email`, `passwordHash`, `isApproved`, `approvedBy`.
*   **Page Routes**:
    *   `/login` (`frontend/app/(auth)/login/page.tsx`)
    *   `/signup/employee` (`frontend/app/(auth)/signup/employee/page.tsx`)
    *   `/signup/analyst` (`frontend/app/(auth)/signup/analyst/page.tsx`)
*   **API Endpoints**:
    *   `POST /api/auth/login` (`frontend/app/api/auth/login/route.ts`)
    *   `POST /api/auth/signup/employee` (`frontend/app/api/auth/signup/employee/route.ts`)
    *   `POST /api/auth/signup/analyst` (`frontend/app/api/auth/signup/analyst/route.ts`)

### Feature 2: OTP Code Generation & Verification
*   **Behavior**:
    *   OTP codes are 6-digit random strings generated by `generateOTP` in `frontend/lib/auth.ts`.
    *   Verification endpoint checks if a matching unused, unexpired OTP exists for the email and purpose.
    *   For employees, verification sets `isVerified: true` and redirects to `/onboarding`.
    *   For analysts, verification returns `pending: true` so the UI shows the under-review screen.
*   **Database Tables**:
    *   `OTPCode`: fields `id`, `email`, `code`, `purpose` (`employee_signup` | `analyst_signup` | `login`), `expiresAt`, `used`, `createdAt`.
    *   `Employee`: updates `isVerified` status.
*   **API Endpoints**:
    *   `POST /api/auth/verify-otp` (`frontend/app/api/auth/verify-otp/route.ts`)
*   **Critical Finding (Headers Bug)**:
    *   In `verify-otp/route.ts`, the server calls `response = setEmployeeCookie(response, ...)` which sets the `Set-Cookie` header on the initial response object.
    *   However, it then returns a new response: `return NextResponse.json({ ...responseData, redirectTo: ... })`. Since headers/cookies are not copied from the original `response` to the new one, the `Set-Cookie` header is discarded! This prevents the browser from receiving the cookie, resulting in a redirect loop to `/login` when the client visits `/onboarding`. E2E tests must verify this behavior and ensure cookies are correctly set.

### Feature 3: Selfie & Geolocation Onboarding (AccessRequest Creation)
*   **Behavior**:
    *   Accessible at `/onboarding`. In the current implementation, it displays an inline webcam feed and requests HTML5 location coordinates.
    *   When the employee clicks "Capture & Request Access", it detects the OS/device type from the User Agent, grabs a frame, and POSTs coordinates and base64 photo data.
*   **Database Tables**:
    *   `AccessRequest`: fields `id`, `employeeName`, `employeeEmail`, `department`, `photoUrl`, `lat`, `lng`, `locationName`, `deviceType`, `status` (`pending` | `approved` | `denied`), `createdAt`.
*   **Page Routes**:
    *   `/onboarding` (`frontend/app/(auth)/onboarding/page.tsx`)
*   **API Endpoints**:
    *   `POST /api/auth/request` (`frontend/app/api/auth/request/route.ts`)

### Feature 4: Access Request Approval/Denial by Analyst
*   **Behavior**:
    *   Analysts access `/access-requests` where the pending requests list polls every 3 seconds.
    *   The page shows user selfie, GPS coordinates in a Google Map embed, and device details.
    *   Analyst can approve or deny the request. Approval creates an active session.
*   **Database Tables**:
    *   `AccessRequest`: updates `status` to `approved` or `denied`.
    *   `Session`: if approved, upserts active session.
*   **Page Routes**:
    *   `/access-requests` (`frontend/app/(dashboard)/access-requests/page.tsx`)
*   **API Endpoints**:

### Feature 5: Zero-Trust Session Issuance & Cookie Validation
*   **Behavior**:

### Feature 7: Audit Log Requests & Approvals

## 2. E2E Test Runner & Harness Design

Because the application is run in headless and resource-constrained subagent environments, a heavy browser-based E2E tool (like Playwright/Puppeteer) is highly volatile and complex to maintain. We propose a custom **Node/TypeScript E2E runner** that operates via HTTP requests and direct DB queries.

### Harness Architecture
The test suite will be located under `frontend/tests/e2e`.

```
frontend/tests/e2e/
├── harness.ts         # Test Client, Cookie Jar, and DB wrapper
├── run.ts             # Test runner CLI, environment configuration, database resets
└── cases/             # Tier 1, 2, 3, and 4 test case definitions
    ├── tier1/
    ├── tier2/
    ├── tier3/
    └── tier4/
```

### Core Components

#### 1. `TestClient` (Virtual Browser Session)
Exposes fetch wrappers that automatically handle:
*   **Cookie Jar**: Saves `Set-Cookie` response headers (like `emp_session` and `analyst_session`) and injects them as `Cookie` request headers for subsequent calls.
*   **Base URL**: Prepends the target local address (e.g. `http://localhost:3000`).
*   **HTML Response Parsing**: Includes helpers to search for layout content, forms, titles, and buttons in returned HTML strings.

```typescript
// Conceptual Harness Client
export class TestClient {
  private cookies: Record<string, string> = {};
  private baseUrl: string = process.env.TEST_BASE_URL || "http://localhost:3000";

  async request(path: string, options: RequestInit = {}): Promise<Response> {
    const headers = new Headers(options.headers || {});
    if (Object.keys(this.cookies).length > 0) {
      const cookieHeader = Object.entries(this.cookies)
        .map(([name, val]) => `${name}=${val}`)
        .join("; ");
      headers.set("Cookie", cookieHeader);
    }

    const response = await fetch(`${this.baseUrl}${path}`, { ...options, headers });
    
    // Parse Set-Cookie headers
    const setCookies = response.headers.getSetCookie();
    for (const cookieStr of setCookies) {
      const parts = cookieStr.split(";")[0].split("=");
      if (parts.length === 2) {
        this.cookies[parts[0].trim()] = parts[1].trim();
      }
    }
    return response;
  }

  clearCookies() { this.cookies = {}; }
}
```

#### 2. Database Asserter
By importing the Next.js project's Prisma client directly (`import prisma from "../../lib/db"`), the test scripts can:
*   Directly verify data writes (e.g. checking that an `AccessRequest` exists and is `pending`).
*   Read transient codes: For OTP verification tests, the test runner reads the generated `code` value directly from SQLite `OTPCode` table, bypassing the mock email delivery.
*   Setup and teardown: Wipe specific tables (`DELETE FROM "Session"`) between test runs to ensure test isolation.

### Tier 3: Cross-Feature Combinations (10 Cases)
Verifies multi-feature business logic, state propagation, and side effects.

*   **Case 3.1: Happy Path E2E pipeline Integration**: Tests the complete employee journey: Signup -> verify OTP -> submit onboarding photo/location -> analyst approve request -> issue session cookie -> fetch employee dashboard.

*   **Case 3.5: Full Forensic Audit Loop**: Analyst creates log request -> Employee grants consent on dashboard -> Agent polls and receives request -> Agent uploads event logs -> Request marked `COMPLETED` -> Analyst opens logs drawer to read historical records.
*   **Case 3.6: Direct Token Issuance Bypassing**: Client attempts to POST to `/api/auth/session/issue` with a fake request ID or a denied request ID. Asserts 403 response, validating that cookie generation is strictly tied to manual approved access requests.
*   **Case 3.7: Risk Score Recalculation on Incident Resolution**: Incident reported -> Alert created -> Analyst resolves incident -> Verification check on employee profile risk score updates and recalculates.
*   **Case 3.8: OTP Timeout and Signup Retry**: Signup -> OTP expires -> Verification fails -> Signup again with updated credentials -> Verifies new OTP is generated and verifies successfully.
*   **Case 3.9: Analyst Approval with Session Cleanup**: Analyst approves request -> Active session is created. Analyst subsequently deletes the employee record. Verifies session is cleaned up or handled gracefully.
*   **Case 3.10: Multi-User Parallel Onboarding**: Multiple employees submit onboarding requests concurrently. Analyst `/access-requests` queue dynamically populates all requests. Analyst approves them in order and each employee is unlocked.

### Tier 4: Real-World Application Scenarios (3 Cases)
Verifies complex, end-to-end security operations scenarios.

#### Case 4.1: Standard Employee Onboarding and Device Setup
1.  Employee signs up via `/signup/employee` (status: unverified).
2.  Gets OTP, verifies it via `/api/auth/verify-otp` (status: verified).
3.  Loads onboarding page, locks GPS location, captures camera selfie, and submits access request.
4.  Employee is held on "Clearance Pending" holding screen, polling the request status.
5.  Analyst logs into the console, visits `/access-requests`, reviews employee selfie and map location, and clicks "Approve & Unlock Devices".
6.  Employee holding screen detects approval, calls `/api/auth/session/issue`, receives `emp_session` cookie, and proceeds to integrations.
7.  Employee enables integrations, causing telemetry logs to generate in SQLite.
8.  Employee accesses dashboard successfully, showing active integration indicators and a low risk score.

#### Case 4.2: Incident Investigation and Device Containment
1.  Employee is logged into dashboard.
2.  Employee reports a suspicious email using the "Report Suspicious Email" form.
3.  SQLite database receives `IncidentReport` and inserts a medium-severity `EmployeeAlert` of type `phishing_detected`.
4.  Analyst logs into the console, visits `/alerts` and `/incidents`, and reviews the suspicious email report details.
5.  Analyst marks incident as `investigating` and adds analyst notes.
6.  Due to high-risk indications, Analyst clicks "Isolate Device" on the employee's containment panel.
7.  Employee dashboard polling detects the `isolated` state, blocks all features, and displays the "Access Revoked" overlay.

#### Case 4.3: Consent-Driven Forensic Investigation
1.  Analyst opens the employee detail page `/users/[id]` in the console.
2.  Under "Consent-Driven Forensics", Analyst fills a start/end time window and clicks "Send Authorization Request".
3.  SQLite database inserts a `LogRequest` in status `PENDING`.
4.  Employee dashboard polling detects the request and displays the "Forensic Audit Request" modal.
5.  Employee reviews the timeframe details and clicks "Grant Access".
6.  The request status updates to `APPROVED`.
7.  The background PowerShell agent polls `/api/log-requests/poll` and receives the approved timeframe.
8.  The agent queries Windows Security logs (interactive logons and process launches), uploads them to `/api/agent` (as `history` telemetry logs), and patches the log request to `COMPLETED`.
9.  Analyst clicks "Check Employee Device Logs" on the profile page, opening the drawer to read the uploaded historical telemetry events.
